# VibeCut production and provider operations

Use when importing, submitting, resuming, placing results or finishing. Model names, prices, supported durations and input limits are live provider facts; query the available connector/catalog and quote before a new choice. Do not treat examples here as a permanent catalog.

## Local tools and project integrity

- Read `shared/project.ts` before manifest writes; supporting tool interfaces are in `tools/README.md`. Source import is `tools/import_source.ts`; `server/source.ts` provides `populateSourceReferences` and `placeSourceRender` for source-aware placements. Pending scenes retain their actual reference picture and aligned source sound.
- Read the current manifest immediately before each update, preserve unrelated creator changes, stable IDs, versions, source provenance and all costs. Increment revision and replace atomically through the existing persistence/store path. Serialize concurrent result writes. Do not edit schema-unknown properties expecting them to survive validation; put richer analysis in a referenced job-relative plan.
- If a repair splits or reallocates source coverage, distinguish the original input interval from each proposed output interval. Validate chronological non-overlapping coverage unless an explicit replay is intended; do not leave the parent covering the full range while adding a child over the same range. Proposed new scene numbers remain tentative until checked against the full live project, not just a scoped review snapshot.
- Keep references labeled and available for comparison. A ready render replaces the corresponding picture and aligned sound in place; the editor uses separate audio placements and mutes embedded video audio. Do not double audio or leave black gaps while waiting. Failed jobs leave references intact. Keep alternate takes as alternatives, not duplicated story events.
- Once a scene's selected photographic set is ready, use `tools/place_scene_images.ts --plan PLAN.json` (dry run), then `--apply`, to show held-image previews before video generation. Supply existing registered active image/version IDs, hashes and full-scene frame spans. The helper preserves source audio/timing, refuses selected videos/custom edits and never approves motion. Keep held/support-only/missing phases pending. Source-aware video placement later removes previews while retaining photographs as assets.
- Save source-derived references, first images, analysis, prompts, requests, receipts, raw outputs, selected assemblies and quality notes in their project/scene-relative folders. Scratch scripts and obsolete experiments belong in `dump`. Local exports stay with their project.
- Write substantial plans/prompts with a file-editing or patch tool, or bounded file writes, rather than embedding an entire plan/script in one shell command. Windows command-line limits can prevent execution before any file is saved. Parse the saved JSON and verify required artifacts exist before reporting completion. Prefer a focused repair delta referencing stable scene IDs to reproducing the whole manifest.
- `tools/assemble_selected_takes.py` selects saved phases using `jobKey` or file, `inSeconds`, `durationSeconds`, and `speed`, retiming native audio together. It supports accepted offscreen voice overlays. Its `flash` option only changes global brightness/saturation: it does **not** draw lightning, projectiles or target-bound effects. `tools/impact_finish.py` adds local post blur/shake/dust; neither tool repairs incorrect mechanics. Inspect the current implementation before relying on a feature.
- Use `tools/apply_remake_batch.ts` for reviewed source-aware result placement. `tools/render_timeline.ts --project UUID --scene N` makes a local saved-scene export; use its supported scope option when reviewing a sequence. Exporting is not a generation request. Keep source references outside the authorized generation scope unsubmitted.

## Routing and photographic inputs

Use the project's chosen Google Cloud Veo model for ordinary coverage, dialogue and straightforward movement with an inspected realistic image. Reserve the project's Higgsfield/Seedance option for difficult rapid multi-body contact or action-camera mechanics where it earns the paid credits. Large optical flow alone does not make a shot complex. Evaluate mechanics and continuity rather than routing by a generic motion score.

When the project has no model preference, inspect available model capabilities/quotes and choose a suitable route within the user's authorized budget. Do not hardcode a particular provider's model or price into the creative plan. Google Cloud grant eligibility and actual billing offsets remain separate from generation cost estimates. Use connectors when sufficient; do not bypass denied permissions.

Use the creator's selected image model for photographic first images and identity/setting references. For GPT use the imagegen skill/tool; for explicitly selected installed Qwen Image 2.1 read `tools/qwen_image21/AI_INSTRUCTIONS.md` and call its existing helper/API. Use [live-action-prompts.md](live-action-prompts.md) for both models' prompts. Save provenance and perform the currently authorized review before video. Reuse compatible photographs/endpoints instead of regenerating unnecessarily; never silently substitute source animation or another provider.

Raw anime video can transfer illustration, held drawings and impossible joint paths alongside motion. Keep source clips, contact sheets and onion skins as analysis evidence. Add them as model inputs only when the provider supports that input and a scoped test demonstrates appropriate photographic style and body mechanics. If a test contaminates the output, use a photographic start image with concise grounded action direction rather than repeatedly feeding the same unsuitable guide. Do not pad a too-short reference with frozen handles or unrelated camera cuts. First/last frames are useful only when their views/states are compatible and the chosen workflow supports them.

Use the requested resolution/frame rate and language. When working under the creator's usual economical live-action settings, these may be 720p, 24fps and English native speech/effects with no music; read the live project/request rather than imposing them on every future video. Verify short dialogue segments and speaker identity. Preserve complete words and aligned sound through trims, sharing and speed changes.

## Batching with actual dependencies

Prepare composition-checked references and a source-ordered action-state plan before video calls. Build a dependency graph: ready independent shots may run concurrently, normally up to three requests or the provider's lower limit. Shots needing an unfinished render's endpoint wait for it. Submit ready siblings before waiting; collect results/failures independently with bounded concurrency or `Promise.allSettled`. Parallel provider calls are not authorization to create extra chats/agents.

Persist intent, model, native duration, estimate/quote and request identity before submission; immediately save operation/job ID and receipt. Store each request in its own scene/job folder. Resume polling existing IDs after an uncertain result; do not resubmit blindly or restart completed siblings. Re-read authorization when the user stops or narrows scope. Explicitly requested continuation resumes only the remaining authorized scope, not another batch of old completed tests.

One take per planned shot is the default review batch. Diagnose a failed take before proposing a paid retry; honor any already-authorized retry allowance and stop limit. Do not introduce repeated approval questions for existing scope, but do not infer unlimited retries from production authorization. Keep rejected results out of the accepted edit. Honor requests to see flawed outputs by labeling them unapproved review takes and retaining their defect notes.

## Budget and receipts

Read `project.costs` and `productionBudget`; totals include historical tests and new/reserved attempts. Keep the recorded retry reserve and user cap. Run `tools/check_generation_budget.ts --project UUID` before a paid batch when using this project's budget schema, replacing planning values with actual provider quotes. A scene group can still need several native requests. Native minimum duration, unused handles and rejected outputs can all cost money; shorter selected runtime and parallel execution do not reduce those charges.

Quote native duration × unit price or the live credit quote, request count and combined batch estimate. Record every attempt by unique provider job/operation ID: provider/model, scene, native seconds, amount/unit, status, scope and receipt. Deduplicate shared-take charges and repeated polling receipts. Resolve ambiguous submission/charge status; unknown means `amount:null`, never zero. Do not call an explicitly non-billed refusal a paid generation without evidence.

Track USD and Higgsfield credits separately. Update the single app-bar `estimatedCostUsd` from recorded/estimated dollar charges to date; do not replace it with a future episode forecast or silently convert credits without a defensible rate. Document unpriced images/analysis, unknown charges and excluded conversions. Do not assume promotional credits have actually paid the bill.

Finish by reporting completed scope, accepted vs review media, residual defects and incurred costs with their limits. Set production status to its real end state; do not leave it running after work has ended. Full automation follows a demonstrated satisfactory workflow, not merely successful API responses.
